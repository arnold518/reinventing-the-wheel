# § 2.5. Flags

`ALU8FlagUnit` derives result flags and selects the carry/overflow signals exposed by the complete ALU. It is combinational: flags describe the current result and operation group, not a previous operation.

| Component | Description | Structural | Behavioral |
| --- | --- | :---: | :---: |
| `ALU8FlagUnit` | Derives zero/negative flags from the selected result and gates arithmetic/shift carry and arithmetic overflow | Yes | Yes |

These columns indicate registered simulator implementations; the simplified C++ examples below are not counted.

The simplified **C++ example** describes binary behavior, not the simulator implementation; it omits propagation delays and `X`/`Z` handling.

## 2.5.1. `ALU8FlagUnit`

The unit consumes an already selected result and status signals from the arithmetic and shift paths. It does not perform arithmetic, select the result word, or decode an opcode.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `RESULT` | Input | 8 | Final selected ALU result |
| `ARITHMETIC` | Input | 1 | Enable arithmetic carry and overflow |
| `SHIFT` | Input | 1 | Enable shift/rotate carry |
| `ARITH_CARRY` | Input | 1 | Carry/no-borrow output of the arithmetic unit |
| `ARITH_OVERFLOW` | Input | 1 | Signed-overflow output of the arithmetic unit |
| `SHIFT_CARRY` | Input | 1 | Carry output of the shifter |
| `ZERO` | Output | 1 | 1 when `RESULT` is zero |
| `NEGATIVE` | Output | 1 | Bit 7 of a binary `RESULT` |
| `CARRY` | Output | 1 | Enabled carry signals combined by OR |
| `OVERFLOW` | Output | 1 | Enabled arithmetic overflow |

There is no `OP`, `C_IN`, `INVALID_OP`, clock, or flag-write input. In particular, the unit does not preserve an old carry when neither group is selected. The shifter itself handles the zero-distance rule that forwards the ALU's `C_IN`.

### Behavior

For binary inputs,

$$
\begin{aligned}
\mathrm{ZERO} &= [\mathrm{RESULT}=0], \\
\mathrm{NEGATIVE} &= \mathrm{RESULT}_7, \\
\mathrm{CARRY} &= (\mathrm{ARITHMETIC}\land\mathrm{ARITH\_CARRY})
\lor(\mathrm{SHIFT}\land\mathrm{SHIFT\_CARRY}), \\
\mathrm{OVERFLOW} &= \mathrm{ARITHMETIC}\land\mathrm{ARITH\_OVERFLOW}.
\end{aligned}
$$

| `ARITHMETIC` | `SHIFT` | `CARRY` | `OVERFLOW` |
| ---: | ---: | --- | --- |
| 0 | 0 | 0 | 0 |
| 1 | 0 | `ARITH_CARRY` | `ARITH_OVERFLOW` |
| 0 | 1 | `SHIFT_CARRY` | 0 |
| 1 | 1 | `ARITH_CARRY OR SHIFT_CARRY` | `ARITH_OVERFLOW` |

The last row is defined by the gates, but does not occur for a settled, known opcode in `ALU8`: its arithmetic and shift groups are mutually exclusive. This is an OR of enabled sources, not an arithmetic-priority multiplexer.

`ZERO` and `NEGATIVE` always describe `RESULT`, independently of these enables. `NEGATIVE` is not an overflow-corrected sign or a comparison result. For example, an overflowing addition can produce `RESULT = 0x80`, `NEGATIVE = 1`, and `OVERFLOW = 1` together.

Comparison operations use subtraction internally, but the complete ALU drives both flag enables low for those operations. Internal subtraction carry/overflow help decide the comparison; they are not exposed as the comparison operation's output flags.

#### C++ example

```cpp
#include <cstdint>

struct Flags8Result {
    bool ZERO;
    bool NEGATIVE;
    bool CARRY;
    bool OVERFLOW;
};

Flags8Result flags8_ref(
    std::uint8_t result, bool arithmetic, bool shift,
    bool arith_carry, bool arith_overflow, bool shift_carry) {
    return {
        result == 0,
        (result & 0x80u) != 0,
        (arithmetic && arith_carry) || (shift && shift_carry),
        arithmetic && arith_overflow,
    };
}
```

The example's inputs are independent, just like the standalone unit's pins; it does not check whether the supplied result and source flags came from the same computation.

#### Unknown inputs and timing

`ZERO` follows the [ZeroDetect8](2.4.md#241-zerodetect8) rules: a known 1 anywhere in `RESULT` establishes `ZERO = 0`; no known 1 and at least one `X`/`Z` produces `ZERO = X`. `NEGATIVE` is `X` when bit 7 is `X` or `Z`; unknown lower bits do not affect it.

A low group enable masks an unknown source flag to zero. A high enable passes a binary flag, or produces `X` from an `X`/`Z` flag. The carry OR can still establish 1 if either enabled contribution is known 1. Unknown enables follow the same AND/OR gate rules; they are not treated as false.

The result and flag sources can arrive at different times. The structural version has no single declared unit latency or atomic flag update. Checkpoints in the recorded scenario inspect settled values; the C++ example does not model propagation or four-state inputs.

### Implementation

#### Structural implementation

| Internal component | Function |
| --- | --- |
| `ZERO_DETECT` (`ZeroDetect8`) | Reduce `RESULT` to the zero flag |
| `RESULT_SPLIT` (`BitSplitter<8>`) | Expose the result sign bit |
| `LOW` and `SIGN` (`ORGate`) | Compute `RESULT[7] OR 0`, converting a high-impedance sign input to unknown logic |
| `ARITH_CARRY_MASK`, `SHIFT_CARRY_MASK` (`ANDGate`) | Gate each carry source with its group enable |
| `CARRY_SELECT` (`ORGate`) | Combine the two masked carry sources |
| `OVERFLOW_SELECT` (`ANDGate`) | Gate arithmetic overflow with `ARITHMETIC` |

The unit contains no flag register. A processor that needs persistent condition codes would store these outputs in a separate stateful component.

#### Behavioral implementation

`Direct8<ALU8FlagUnit>` calls `flags`. It reduces `RESULT` for `ZERO`, evaluates `RESULT[7] OR 0` for `NEGATIVE`, and masks/combines the carry and overflow inputs with four-state AND/OR functions. It stores no flags and does not impose priority when both group enables are high.

The evaluator is defined in [ALU8Behavioral.cpp](https://github.com/arnold518/reinventing-the-wheel/blob/github-pages/src/modules/composite/ALU8Behavioral.cpp); its value functions are in [ALU8ValueModel.hpp](https://github.com/arnold518/reinventing-the-wheel/blob/github-pages/src/modules/composite/ALU8ValueModel.hpp). It retains the public pins and schedules outputs with one abstract delay tick, without internal circuit objects or gate-propagation glitches.

The recorded scenario runs against both implementations in CTest. [ALU8FidelityContractTest](https://github.com/arnold518/reinventing-the-wheel/blob/github-pages/src/tests/ALU8BehavioralTests.cpp) checks binary/X/Z settled-output equivalence against the structural circuit. The example table uses the default structural run; its checkpoint times need not match the behavioral run.

# § 2.1. Arithmetic Components

This page builds word arithmetic from one-bit cells. Two word adders compute the same sum with different carry networks: `RippleCarryAdder<W>` passes the carry through W full adders, and `ParallelPrefixAdder<W>` combines carries in log₂(W) levels. [Ripple versus prefix carry](#ripple-versus-prefix-carry) compares them. `AddSub<W>` and `ArithmeticUnit<W>`, and every ALU in this project, use the faster prefix adder.

Bits are numbered from 0 at the least significant position. Let $M=2^W$ and $S=2^{W-1}$. Results wrap modulo M; signed values range from $-S$ to $S-1$. Carry is unsigned carry/no-borrow and is independent of signed overflow. These are combinational components with no clock or stored flags.

| Component | Description | Structural | Behavioral |
| --- | --- | :---: | :---: |
| `HalfAdder` | One-bit sum and carry, without carry-in | Yes | Yes |
| `FullAdder` | One-bit addition with carry-in | Yes | Yes |
| `RippleCarryAdder<W>` | Word adder built from W chained full adders | Yes | Yes |
| `ParallelPrefixAdder<W>` | Word adder with a logarithmic-depth carry network | Yes | Yes |
| `AddSub<W>` | Addition or subtraction with a carry input and signed overflow | Yes | Yes |
| `ArithmeticUnit<W>` | Seven arithmetic operations over one shared add/subtract path | Yes | Yes |

W is **8, 16 or 32**. The fidelity columns describe the recorded configuration of each section. The word units have a compact form at every width; `HalfAdder` and `FullAdder` have the gate-list compact form, chosen only explicitly. The C++ references take W as a template parameter. [Construction and selection](2.6.md#construction-and-selection) describes construction.

## 2.1.1. `HalfAdder`

`HalfAdder` adds two one-bit operands. It has no carry input, so it cannot by itself be a general cell in a multi-bit carry chain.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `A` | Input | 1 | First operand bit |
| `B` | Input | 1 | Second operand bit |
| `Sum` | Output | 1 | Low bit of the sum |
| `Carry` | Output | 1 | Carry into the next bit position |

The output is named `Carry`, not `Carry_out` or `Cout`. Pin names are case-sensitive.

### Behavior

For binary inputs,

$$
\begin{aligned}
\mathrm{Sum} &= A \oplus B, \\
\mathrm{Carry} &= A \land B.
\end{aligned}
$$

Interpreting the bits as unsigned integers, `A + B = Sum + 2*Carry`. For example, `1 + 1` gives `Sum = 0`, `Carry = 1`. The component has no clock, stored state, or flags beyond this carry.

#### C++ example

```cpp
struct HalfAdderResult {
    bool Sum;
    bool Carry;
};

HalfAdderResult half_adder_ref(bool a, bool b) {
    return {a != b, a && b};
}
```

This binary-only function describes the settled outputs. It is not a registered behavioral implementation.

#### Unknown inputs

The simulator's XOR produces `X` if either input is `X` or `Z`. The AND produces 0 if either input is definitely 0, 1 only if both are definitely 1, and `X` otherwise. Neither output drives `Z`.

| `A` | `B` | Settled `Sum` | Settled `Carry` |
| --- | --- | --- | --- |
| 0 | `X` or `Z` | `X` | 0 |
| 1 | `X` or `Z` | `X` | `X` |

### Implementation

#### Structural implementation

Both inputs fan out to two gates, which operate in parallel:

| Child | Type | Inputs → output |
| --- | --- | --- |
| `XOR1` | `XORGate` | `A`, `B` → `Sum` |
| `AND1` | `ANDGate` | `A`, `B` → `Carry` |

There is no internal carry chain or storage. `HalfAdder` has only this structural implementation; the two gates remain visible in the simulator.

#### Behavioral implementation

The compact form evaluates this part's own gate list, flattened once from its structural form, and publishes the settled values on the delays proven on those gates ([§ 1.1 Structural and compact forms](../basic/1.1.md#structural-and-compact-forms)). Its values are the gates' by construction, including unknown and floating inputs; `GateListCompactEquivalenceTest` checks them. It is chosen only explicitly, for example by collapsing the part in the simulator; profiles that prefer compact forms keep the gates.

## 2.1.2. `FullAdder`

`FullAdder` adds two one-bit operands and a carry input. Its carry output can feed the next bit position; W such cells form `RippleCarryAdder<W>`.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `A` | Input | 1 | First operand bit |
| `B` | Input | 1 | Second operand bit |
| `Carry_in` | Input | 1 | Carry from the previous bit position |
| `Sum` | Output | 1 | Low bit of the three-input sum |
| `Carry_out` | Output | 1 | Carry into the next bit position |

The one-bit cells keep the names `Carry_in` and `Carry_out`; the word adders use `C_IN` and `C_OUT`.

### Behavior

Define the first half adder's sum as `P = A XOR B`. For binary inputs,

$$
\begin{aligned}
\mathrm{Sum} &= P \oplus \mathrm{Carry\_in}, \\
\mathrm{Carry\_out} &= (A \land B) \\
&\quad \lor (P \land \mathrm{Carry\_in}).
\end{aligned}
$$

Thus `A + B + Carry_in = Sum + 2*Carry_out`. With three input ones, the result is `Sum = 1`, `Carry_out = 1`; with exactly two ones, it is `Sum = 0`, `Carry_out = 1`. The carry is not a signed-overflow indication.

#### C++ example

```cpp
struct FullAdderResult {
    bool Sum;
    bool Carry_out;
};

FullAdderResult full_adder_ref(bool a, bool b, bool carry_in) {
    const auto first = half_adder_ref(a, b);
    const auto second = half_adder_ref(first.Sum, carry_in);
    return {second.Sum, first.Carry || second.Carry};
}
```

This example reuses `half_adder_ref` above and follows the actual two-half-adder composition. It describes binary settled values, not simulator events or a selectable behavioral implementation.

#### Unknown inputs

`X`/`Z` inputs propagate through the two half adders and final OR gate. Use the stated XOR/AND/OR network, not an arbitrary binary-equivalent rewrite, to determine four-state results. For example:

| `A` | `B` | `Carry_in` | Settled `Sum` | Settled `Carry_out` |
| --- | --- | --- | --- | --- |
| 0 | 0 | `Z` | `X` | 0 |
| 1 | 1 | `X` | `X` | 1 |
| 1 | `X` | 1 | `X` | `X` |

In the last row, both the first sum and both intermediate carries are unknown. The binary-equivalent majority expression `(A AND B) OR (A AND Carry_in) OR (B AND Carry_in)` would instead yield carry 1 because `A AND Carry_in = 1`. That is **not** this structural circuit's four-state contract. Neither output drives `Z`.

### Implementation

#### Structural implementation

| Child | Type | Inputs → output |
| --- | --- | --- |
| `HA1` | `HalfAdder` | External `A`, `B` → intermediate sum and first carry |
| `HA2` | `HalfAdder` | `HA1.Sum`, external `Carry_in` → external `Sum` and second carry |
| `OR1` | `ORGate` | `HA1.Carry`, `HA2.Carry` → external `Carry_out` |

Expanding the two half adders reveals five primitive gates in total: two XORs, two ANDs, and one OR. There is no stored carry or clock. `FullAdder` has only this structural implementation.

In `RippleCarryAdder<8>`, `C_IN` drives `FA0.Carry_in`, each cell's `Carry_out` drives the next cell's `Carry_in`, and `FA7.Carry_out` drives `C_OUT`. This is a ripple-carry connection, not eight independent additions.

**Timing.** The carry's longest path is `HA1.XOR1 → HA2.AND1 → OR1` (an XOR, an AND and an OR); the sum's is two XOR gates. Which is longer depends on the profile: in `unit` every gate is one tick, so the carry path is longer; in the realistic profiles an XOR costs about four inverter delays, so the sum path is.

#### Behavioral implementation

The compact form evaluates this part's own gate list, flattened once from its structural form, and publishes the settled values on the delays proven on those gates ([§ 1.1 Structural and compact forms](../basic/1.1.md#structural-and-compact-forms)). Its values are the gates' by construction, including unknown and floating inputs; `GateListCompactEquivalenceTest` checks them. It is chosen only explicitly, for example by collapsing the part in the simulator; profiles that prefer compact forms keep the gates.

## 2.1.3. `RippleCarryAdder<W>`

`RippleCarryAdder<W>` chains W full adders. It is the direct word-level extension of § 2.1.2 and the reference for the faster adder below.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `A`, `B` | Input | W each | Unsigned operand patterns |
| `C_IN` | Input | 1 | Carry into bit 0 |
| `OUT` | Output | W | Low W bits of the sum |
| `C_OUT` | Output | 1 | Carry out of bit W−1 |

### Behavior

For $T=A+B+\mathrm{C\_IN}$, `OUT = T mod M` and `C_OUT = [T >= M]`. There are no signed-overflow, zero or negative outputs. To add wider words, connect one adder's `C_OUT` to the next adder's `C_IN`: `0x00FF + 0x0001` gives a low byte of `0x00` with carry 1, then an upper byte of `0x01`.

#### C++ example

This binary reference is parameterized by W = 8, 16 or 32. Inputs must fit their pin widths. It omits propagation delays and X/Z values.

```cpp
#include <cstdint>

// Binary word domain used by the references in this chapter.
template<unsigned W>
struct WordReference {
    static_assert(W == 8 || W == 16 || W == 32);
    static constexpr std::uint64_t mask = (std::uint64_t{1} << W) - 1;
    static constexpr std::uint64_t sign = std::uint64_t{1} << (W - 1);
};

template<unsigned W>
struct AdderResult {
    std::uint32_t OUT;
    bool C_OUT;
};

template<unsigned W>
AdderResult<W> adder_ref(std::uint32_t a, std::uint32_t b, bool c_in) {
    const std::uint64_t total = std::uint64_t(a) + b + c_in;
    return {
        static_cast<std::uint32_t>(total & WordReference<W>::mask),
        total >= (WordReference<W>::mask + 1),
    };
}
```

#### Unknown inputs

Each bit follows the full adder's XOR/AND/OR equations. A known controlling input can mask an unknown one, so an unknown bit does not automatically make the whole word unknown. The recording below drives bit 0 of `A` to X and to Z with `B = 0` and `C_IN = 0`: only `OUT[0]` becomes X, and `C_OUT` stays 0.

### Implementation

#### Structural implementation

Two `BitSplitter<W>` parts separate the operand bits, W `FullAdder` cells `FA0`…`FA(W−1)` add them, and a `BitJoiner<W>` assembles `OUT`. `C_IN` feeds `FA0`; each `Carry_out` feeds the next cell; the last cell drives `C_OUT`. The carry path therefore grows linearly with W.

#### Behavioral implementation

The compact form computes the same ripple recurrence bit by bit with four-state values, so its outputs match the gates for every input, including X and Z. It exists at W = 8, 16 and 32 and runs on delays proven on this circuit.

**Timing.** These paths describe the eight-bit adder in each timing profile:

## 2.1.4. `ParallelPrefixAdder<W>`

`ParallelPrefixAdder<W>` computes the same sum as `RippleCarryAdder<W>`, but finds every carry in log₂(W) combining levels instead of W chained cells. Every ALU in this project uses it.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `A`, `B` | Input | W each | Operand patterns |
| `C_IN` | Input | 1 | Carry into bit 0 |
| `OUT` | Output | W | Low W bits of the sum |
| `C_OUT` | Output | 1 | Carry out of bit W−1 |
| `C_SIGN` | Output | 1 | Carry into bit W−1, the sign bit |

### Behavior

`OUT` and `C_OUT` follow the same rule as `RippleCarryAdder<W>`. `C_SIGN` is the carry into the sign bit; signed overflow of the addition is `C_SIGN XOR C_OUT`, which the [RV32I ALU](../rv32i/4.3/alu.md) uses.

#### C++ example

The reference reuses `adder_ref<W>` and `WordReference<W>` from § 2.1.3. Inputs must fit W bits.

```cpp
template<unsigned W>
struct PrefixAdderResult {
    std::uint32_t OUT;
    bool C_OUT;
    bool C_SIGN;
};

template<unsigned W>
PrefixAdderResult<W> prefix_adder_ref(std::uint32_t a, std::uint32_t b, bool c_in) {
    const auto sum = adder_ref<W>(a, b, c_in);
    const auto low_mask = WordReference<W>::sign - 1;
    const bool carry_into_sign = ((a & low_mask) + (b & low_mask) + c_in)
                                  >= WordReference<W>::sign;
    return {sum.OUT, sum.C_OUT, carry_into_sign};
}
```

#### Unknown inputs

Propagate/generate cells and combining levels use four-state XOR/AND/OR gates. The combination `G = G_high OR (P_high AND G_low)` is the ripple carry equation regrouped, so an unknown bit spreads the same way as in `RippleCarryAdder<W>`. The adder comparison test finds identical outputs for the two 32-bit adders on 3,136 binary and four-state rows.

### Implementation

#### Structural implementation

The word gates `PROPAGATE` (`XORGate<W>`) and `GENERATE` (`ANDGate<W>`) give every bit's propagate `pᵢ = Aᵢ XOR Bᵢ` and generate `gᵢ = Aᵢ AND Bᵢ` at once (one-bit gates, grouped as words; see [word gates](../basic/1.3.md#137-andgatew)). A carry group is the transformation `c_out = G OR (P AND c_in)`; `CarryCombine` joins two neighbouring groups as `G = G_high OR (P_high AND G_low)`, `P = P_high AND P_low`. Levels `PREFIX_1`, `PREFIX_2`, `PREFIX_4`, … combine groups at distances 1, 2, 4, …, so W = 8, 16 and 32 need 3, 4 and 5 levels. The word gates `CIN` (AND with `C_IN` on every bit) and `CARRY` (OR) give the carry out of every bit; the wiring part `CARRY_BITS` shifts it up one bit, with `C_IN` into bit 0, and also yields `C_SIGN` and `C_OUT`; the word gate `SUM` (XOR with the propagates) forms `OUT`.

#### Behavioral implementation

The compact form evaluates the same propagate/generate levels with four-state values and matches the gates for every input. It exists at W = 8, 16 and 32 and runs on delays proven on this circuit.

## Ripple versus prefix carry

Both adders compute the same function; they differ only in how long the carry takes. A ripple adder's worst path crosses all W full adders, so it grows linearly with W. A prefix adder's worst path crosses log₂(W) combining levels plus a few gates at each end, so it grows with the logarithm of W.

The rows below are the proven worst-case delays of each adder from an operand to the carry out, read from the same delay tables the compact forms use. `unit` counts gates (one tick each); `embedded` and `desktop` are the 65 nm and 32 nm profiles in picoseconds.

<!-- timing-rows
RippleCarryAdder<8> | word.ripple-carry-adder.8.behavioral | A → C_OUT
ParallelPrefixAdder<8> | word.parallel-prefix-adder.8.behavioral | A → C_OUT
RippleCarryAdder<16> | word.ripple-carry-adder.16.behavioral | A → C_OUT
ParallelPrefixAdder<16> | word.parallel-prefix-adder.16.behavioral | A → C_OUT
RippleCarryAdder<32> | word.ripple-carry-adder.32.behavioral | A → C_OUT
ParallelPrefixAdder<32> | word.parallel-prefix-adder.32.behavioral | A → C_OUT
-->

Each doubling of W doubles the ripple adder's carry delay (17, 33 and 65 gate delays in `unit`) but adds only one combining level to the prefix adder (8, 10 and 12). The prefix adder is already faster at 8 bits; at 32 bits it is about 5.4 times faster in `unit` and about 5 times faster in the realistic profiles. The price is area: the prefix network adds a combining cell for most bits at every level. Because carry delay dominates word arithmetic, `AddSub<W>`, both ALUs and the RV32I branch-target adders use the prefix adder.

The same comparison runs as a test: `ArithmeticTimingOptimizationTest` builds both adders at W = 8, 16 and 32 in all three timing profiles and requires the prefix adder to settle sooner and to contain carry levels. It also drives both 32-bit adders with 3,136 binary and four-state rows and requires identical outputs. The [`ripple-carry-adder-w16`](../../simulator/?scenario=ripple-carry-adder-w16) recording repeats the prefix adder's eight 16-bit cases, so the two circuits can be compared side by side in the simulator.

## 2.1.5. `AddSub<W>`

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `A`, `B` | Input | W each | Operand patterns |
| `SUB` | Input | 1 | Invert every B bit when high |
| `C_IN` | Input | 1 | Carry into the adder |
| `OUT` | Output | W | Wrapped result |
| `C_OUT` | Output | 1 | Addition carry, or no-borrow for subtraction |
| `OVERFLOW` | Output | 1 | Signed result outside −S…S−1 |

### Behavior

Let $B'=B$ when SUB=0 and $B'=M-1-B$ when SUB=1. The adder computes $T=A+B'+\mathrm{C\_IN}$; `OUT` is T modulo M and `C_OUT` is `[T >= M]`.

| SUB | C_IN | Result before wrapping |
| ---: | ---: | --- |
| 0 | 0 | A + B |
| 0 | 1 | A + B + 1 |
| 1 | 1 | A − B |
| 1 | 0 | A − B − 1 |

`SUB` only inverts B; `C_IN` stays a separate input, so ordinary subtraction needs `C_IN = 1`. For subtraction, `C_OUT` is `[A >= B + (1 − C_IN)]`, so 1 means no borrow. Signed overflow uses the operand and result signs: `NOT(A_sign XOR B'_sign) AND (A_sign XOR OUT_sign)`.

To subtract wider words, start the lowest word with `SUB = 1, C_IN = 1` and connect each `C_OUT` to the next word's `C_IN`. For `0x0100 − 0x0001` in bytes, the low byte gives `0xFF` with `C_OUT = 0` (a borrow); the upper byte then gives `0x00` with `C_OUT = 1`.

#### C++ example

This binary reference reuses `adder_ref<W>` from § 2.1.3. It omits propagation delays and X/Z values.

```cpp
template<unsigned W>
struct AddSubResult {
    std::uint32_t OUT;
    bool C_OUT;
    bool OVERFLOW;
};

template<unsigned W>
AddSubResult<W> addsub_ref(
    std::uint32_t a, std::uint32_t b, bool sub, bool c_in) {
    const auto effective_b = static_cast<std::uint32_t>(
        b ^ (sub ? WordReference<W>::mask : 0x00u));
    const auto sum = adder_ref<W>(a, effective_b, c_in);
    const bool same_sign = ((a ^ effective_b) & WordReference<W>::sign) == 0;
    const bool result_changed_sign = ((a ^ sum.OUT) & WordReference<W>::sign) != 0;
    return {sum.OUT, sum.C_OUT, same_sign && result_changed_sign};
}
```

#### Unknown inputs

Conditional inversion, carry propagation and the sign logic use four-state gates. An unknown `SUB` or `C_IN` follows those gates rather than an assumed Boolean value.

### Implementation

#### Structural implementation

The word gate `B_XOR_SUB` (`XORGate<W>`, one XOR per bit) forms B′ from B and `SUB`, spread across the word by the wiring part `SUB_WORD`. One `ParallelPrefixAdder<W>`, named `ADD`, computes A + B′ + C_IN. Splitters expose the sign bits, and XOR/NOT/AND gates produce `OVERFLOW` from them.

#### Behavioral implementation

The compact form, available at W = 8, 16 and 32, computes the settled outputs of these gates in one step. It keeps the gates' Boolean factoring, so X and Z inputs give the same outputs as the structural circuit, and it runs on delays proven on that circuit.

## 2.1.6. `ArithmeticUnit<W>`

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `A`, `B` | Input | W each | Primary and secondary operands |
| `OP` | Input | 3 | Local arithmetic selector |
| `C_IN` | Input | 1 | Carry/no-borrow input for ADC/SBC |
| `OUT` | Output | W | Selected arithmetic result |
| `CARRY` | Output | 1 | Carry or no-borrow |
| `OVERFLOW` | Output | 1 | Signed overflow |
| `INVALID_OP` | Output | 1 | Local opcode 7 |

### Behavior

One shared `AddSub<W>` performs the selected operation. Results wrap modulo M.

| Local OP | Operation | Result before wrapping | Carry input used? |
| ---: | --- | --- | --- |
| 0 | ADD | A + B | No |
| 1 | ADC | A + B + C_IN | Yes |
| 2 | SUB | A − B | No |
| 3 | SBC | A − B − (1 − C_IN) | Yes |
| 4 | INC | A + 1 | No |
| 5 | DEC | A − 1 | No |
| 6 | NEG | 0 − A | No |
| 7 | Reserved | OUT=0, CARRY=0, OVERFLOW=0, INVALID_OP=1 | No |

<a id="arithmetic-flags"></a>

For INC, carry means A=M−1 and overflow means A=S−1. For DEC, no-borrow means A≠0 and overflow means A=S. For NEG, no-borrow means A=0 and overflow means A=S. The other overflow cases follow the range of the signed result. `INVALID_OP` reports an encoding, not uncertainty in the operands. The complete ALU's arithmetic codes 0–6 equal these local codes.

#### C++ example

This binary reference reuses `addsub_ref<W>` from § 2.1.5. It omits propagation delays and X/Z values.

```cpp
template<unsigned W>
struct ArithmeticResult {
    std::uint32_t OUT;
    bool CARRY;
    bool OVERFLOW;
    bool INVALID_OP;
};

template<unsigned W>
ArithmeticResult<W> arithmetic_ref(
    std::uint32_t a, std::uint32_t b, std::uint32_t op, bool c_in) {
    std::uint32_t x = a;
    std::uint32_t y = b;
    bool sub = false;
    bool carry_in = false;

    switch (op) {
    case 0x00: break;                                      // ADD
    case 0x01: carry_in = c_in; break;                     // ADC
    case 0x02: sub = true; carry_in = true; break;          // SUB
    case 0x03: sub = true; carry_in = c_in; break;          // SBC
    case 0x04: y = 0; carry_in = true; break;               // INC
    case 0x05: y = 1; sub = true; carry_in = true; break;   // DEC
    case 0x06: x = 0; y = a; sub = true;
               carry_in = true; break;                    // NEG
    default: return {0, false, false, true};
    }

    const auto result = addsub_ref<W>(x, y, sub, carry_in);
    return {result.OUT, result.C_OUT, result.OVERFLOW, false};
}
```

#### Unknown inputs

Operand multiplexers isolate ignored inputs: NEG ignores B and C_IN, and INC/DEC ignore B. The reserved code masks result, carry and overflow to zero. Unknown selector bits follow the gate-built multiplexers.

### Implementation

#### Structural implementation

Opcode-controlled operand and carry multiplexers, constants, one `AddSub<W>` and reserved-operation masks form the circuit; the result mask is the word gate `RESULT_MASK` (`ANDGate<W>`, the valid bit spread across the word). SUB uses carry-in 1; SBC uses C_IN. INC selects B = 0 and carry 1; DEC selects B = 1, SUB = 1 and carry 1; NEG selects A = 0, B = the original A, SUB = 1 and carry 1.

#### Behavioral implementation

The compact form, available at W = 8, 16 and 32, computes the settled outputs of these gates in one step. It keeps the gates' Boolean factoring, so X and Z inputs give the same outputs as the structural circuit, and it runs on delays proven on that circuit.

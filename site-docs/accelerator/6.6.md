# § 6.6. Experiments

The questions, fixed before any run:

1. How much faster is the computer with the matrix unit than the computer
   alone, on matrix multiplies and on the two networks?
2. How does that change with the array size (4 × 4, 8 × 8, 16 × 16)?
3. How does it change with the main memory (flip-flop, SRAM, DRAM)?
4. What limits the unit: the multiplying, or moving data and commands?

## Setup

| Item | Setting |
| --- | --- |
| Machines | `accelerator-machine-cpu` (the CPU alone) and `accelerator-machine` with `MatrixUnit<N>` |
| Core | RV32IM five-stage, `multiplier=array` on both machines, so the CPU is not held back by a 33-edge multiply |
| Bus | The pipelined bus of [6.3.2](6.3.md#632-the-pipelined-bus) on both machines, except where a row says otherwise |
| Fidelity | Compact (every part on the delays proven on its gates) |
| Timing | The `unit` timing profile, 1000-tick clock; no setup violation in any run |
| Memories | FF; SRAM, the clocked macro with its wait states at this clock; DRAM with the profile's 2-word rows and no refresh, and a row retention of 64 ms (a real DRAM's refresh period) instead of the profile's 1 ms ([below](#dram-retention)) |
| Programs | [6.5](6.5.md): matrix multiply (three layers), MLP and CNN; two images with the unit, one on the CPU alone |
| Tool | `accelerator_experiment --program … --matrix … --memory … --array-multiplier --pipelined-bus`, driven by `tools/accelerator/run-campaign.py` |

Cycles are the program's own timer readings around each timed section; a
cycle is one clock period on every machine. A clock certificate for these
machines in the realistic profiles was not made, so this section reports
cycles, not seconds.

## Results

Every run halted cleanly, with status 0 and no setup violation, and its
outputs equal the host reference: the scores of `model.json` for the
networks, and the CPU-alone products for the matrix multiplies.

### 1–2. Speedup and array size

Cycles of the timed section, SRAM main memory:

| Workload | CPU alone | 4 × 4 | 8 × 8 | 16 × 16 | Speedup at 16 × 16 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Matrix multiply (3 layers) | 2,851,206 | 71,167 | 29,984 | 26,614 | 107.1× |
| MLP, one image | 1,636,072 | 462,490 | 137,032 | 117,321 | 13.9× |
| CNN, one image | 2,643,442 | 106,281 | 49,697 | 46,111 | 57.3× |

The CPU alone needs 32–45 cycles per multiply-add: a load of each operand,
the multiply, the add and the loop. The 16 × 16 unit reaches 3.9
multiply-adds per cycle on the largest matrix multiply, 1.3 on the CNN and
0.43 on the MLP, against a peak of 256.

Going from 4 × 4 to 8 × 8 pays (2.1–3.4× fewer cycles); going on to
16 × 16 barely does (8–17 %). Each layer has too few rows and too few
outputs to keep a 16-wide array full, and the work that does not shrink
with the array (copying, commands) is already most of the time.

### 3. Main memory

Cycles of the timed section, 16 × 16 unit:

| Workload | FF | SRAM | DRAM |
| --- | ---: | ---: | ---: |
| Matrix multiply (3 layers) | 18,428 | 26,614 | 55,424 |
| MLP, one image | 89,462 | 117,321 | 208,728 |
| CNN, one image | 32,571 | 46,111 | 91,456 |

Every step to a slower memory costs the unit 30–110 %, because the unit
waits on the copy engine, which holds one request at a time. The MLP is the
extreme case: each weight is fetched once and used for one multiply-add.
Two images as one batch cost little more than one (16 × 16, SRAM: 119,354
cycles against 117,321), because the weight tiles are loaded once for both;
with batch 1, the MLP is bound by moving weights. The first TPU's own
measurements show the same split: its MLPs and LSTMs were limited by weight
memory bandwidth, its CNNs by the multipliers (Jouppi et al., *In-Datacenter
Performance Analysis of a Tensor Processing Unit*, ISCA 2017).

### 4. What limits the unit

The edges in which the array, the shift engine or the activate engine is
busy, counted from each layer's commands, against the measured cycles
(SRAM):

| Unit | Layer | Array, shift, activate edges | Measured cycles | Busy share |
| --- | --- | ---: | ---: | ---: |
| 4 × 4 | 4 × 32 → 16 | 496 | 6,524 | 8 % |
| 4 × 4 | 8 × 64 → 32 | 2,496 | 21,633 | 12 % |
| 4 × 4 | 16 × 64 → 64 | 7,168 | 43,010 | 17 % |
| 8 × 8 | 4 × 32 → 16 | 224 | 2,728 | 8 % |
| 8 × 8 | 8 × 64 → 32 | 1,024 | 8,397 | 12 % |
| 8 × 8 | 16 × 64 → 64 | 2,624 | 18,859 | 14 % |
| 16 × 16 | 4 × 32 → 16 | 106 | 2,450 | 4 % |
| 16 × 16 | 8 × 64 → 32 | 456 | 7,494 | 6 % |
| 16 × 16 | 16 × 64 → 64 | 1,072 | 16,670 | 6 % |

The array computes in at most a sixth of the time. The rest is the copy
engine: one bus request in flight, one byte per cycle from a held word, and
one byte write per request for results. The next steps for a faster unit are
therefore on the data side: a wider or burst DMA (the router passes no
bursts today), a router with two requests in flight, and reusing loaded
weights across a batch, rather than a larger array.

### The bus and the multiplier

The same matrix multiply on the chapter-5 bus with the iterative multiplier
(`-plain` runs), cycles per layer:

| Machine | 4 × 32 → 16 | 8 × 64 → 32 | 16 × 64 → 64 |
| --- | ---: | ---: | ---: |
| CPU alone | 73,721 | 555,762 | 2,221,723 |
| CPU alone, chapter-5 bus and multiplier | 155,425 | 1,185,409 | 4,739,849 |
| 16 × 16 | 2,450 | 7,494 | 16,670 |
| 16 × 16, chapter-5 bus and multiplier | 3,107 | 8,389 | 18,146 |

The array multiplier and the pipelined bus together halve the CPU's time
(the same 729,492 instructions in 3.23 million cycles instead of 6.56
million). The unit's layers take 8–21 % fewer cycles: its copy engine also
waits longer for each request on the chapter-5 bus, and the processor
issues its commands more slowly. Measured on the old setup, the
16 × 16 unit's speedup on the largest layer would have been 261× instead of
133×: an accelerator compared with a slowed-down CPU looks better than it is.

### DRAM retention

The `unit` timing profile gives DRAM 2-word rows, no refresh, and a
retention of 10⁹ ticks: 1,000,000 cycles at this clock. A row that nobody
opens for longer reads as unknown (X), as a real DRAM without refresh loses
its data ([DRAM device](../memory/technologies/dram.md)). The
matrix-multiply program runs 1.76 million cycles, most of it making
operands; with the profile's retention its last code (printing `done` and
halting), untouched since it was loaded, read as X and the core stopped
after cycle 1,758,436. The runner now reports such a run at once.

The DRAM runs therefore set the memory's `retention_ticks` to 64 ms, a real
DRAM's refresh period (the realistic profiles' value). Retention decides
only whether a row's data survives, not how long an access takes: the MLP
and CNN runs gave the same cycles, instructions, outputs and simulation
event counts with either retention. The cause was confirmed on the small
`demo-cpu` program with the profile's retention and a 50 times longer
clock period (retention: 20,000 cycles): it turns X at cycle 37,416 on the
pipelined bus and at 24,715 on the chapter-5 bus, and halts cleanly in
78,291 cycles at the normal period.

These DRAM figures include no refresh time. Refreshing all 32,768 rows
within 64 ms would take one refresh (about ten cycles) every 1,953 cycles,
about 0.5 % of the memory's time; the profile has no refresh interval to
set it from.

## Reproducing a run

With the built native tool, one run of the campaign is, for example:

```sh
build-accel/accelerator_experiment --program matmul-n16 --matrix 16 --memory dram \
  --array-multiplier --pipelined-bus --dram-retention 64000000000
```

It runs a new simulation and prints the run as JSON (cycles, instructions,
timed sections, outputs, unit commands, host time).
`tools/accelerator/run-campaign.py run` runs every configuration of this
page serially, each in its own memory-capped scope, and skips those with a
result already; `run-campaign.py table` checks every saved run against the
references and prints the tables above. Reformatting a table is not a new
run.

## Limits

- Cycles, not seconds: no clock certificate was made for these machines.
- The pipelined bus and the array multiplier are options on both machines;
  the chapter 3–5 machines keep their default bus and multiplier.
- One timed run per configuration; the simulation is deterministic, so a
  repeat gives the same cycles.
- The CPU-alone programs are plain C compiled with GCC `-O2`, not hand-tuned.

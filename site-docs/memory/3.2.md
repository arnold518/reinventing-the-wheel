# § 3.2. Memory Transactions

A shared, versioned transaction interface above the native devices in [3.1](3.1/index.md). It is a single-outstanding, aligned-word protocol, not AXI, a DDR interface, or a coherent interconnect. Width W is 8, 16, or 32; capacity is a construction parameter.

The transaction components are:

| Component | Description | Structural | Behavioral |
| --- | --- | :---: | :---: |
| `MemoryTransactionPort<W>` | Track one delayed request; pass through or hold its response | Yes | No |
| `MemoryResponseBuffer<W>` | One-entry response buffer with a combinational bypass | Yes | No |
| `ClockedStateBit` | Resettable always-clocked bit for handshake state; a storage component documented in [4.3.1](../rv32i/4.3/register.md) | Yes | Yes |

## Protocol rules

Request and response transfers occur on a known rising `CLK` edge when the corresponding VALID and READY are both 1. The sender holds VALID and its payload until transfer; it must not wait for READY before asserting VALID. At most one request is outstanding. The response is held unchanged until consumed. A new request may be accepted on the response-consume edge. A zero-wait endpoint may present its response during the request cycle and transfer both on the same edge. This is protocol version 2; old version-1 recordings may have different timing.

Addresses are **byte addresses** aligned to W/8. Reads return a full word. Writes/programs use positioned byte lanes; mask bit b enables byte b. ISA load sizes, sign extension, unaligned splitting, bursts, atomics, arbitration and caching are outside this port.

| `REQ_OP` | Operation | Meaning |
| ---: | --- | --- |
| 0 | READ | Read one aligned word |
| 1 | WRITE | Replace enabled bytes in writable FF/SRAM/DRAM |
| 2 | PROGRAM | NOR flash only: clear enabled bits, never restore 0→1 |
| 3 | ERASE_BLOCK | NOR flash only: restore one whole block to ones; address must be block-aligned |
| 4–7 | Reserved | Unsupported-operation response |

| `RSP_STATUS` | Meaning |
| ---: | --- |
| 0 | Success |
| 1 | Misaligned word/block address |
| 2 | Address outside configured capacity |
| 3 | Attempt to modify ROM |
| 4 | Unsupported operation |
| 5 | Native device failure |
| 6 | Unknown required request fields |
| 7 | Reserved |

Error and non-read responses have zero data. Unknown stored bits remain X even with a successful read. A zero write mask does not change contents. Read requests ignore write data/mask; erase ignores both. Validation order is unknown opcode/address → reserved opcode → required mask → word alignment → capacity → technology permission/block alignment.

`RST` resets the **transaction interface**, not memory contents. It suppresses VALID/READY and discards response delivery. An already launched native sequence drains before reuse; its writes/programs/erases are not rolled back. Native FF storage reset is deliberately not tied to this interface reset.

## 3.2.1. `MemoryTransactionPort<W>`

Shared structural frontend. The backend captures the live request on an edge with START=1 and holds DONE/result until an edge with FINISH=1. It owns no memory contents and does not itself validate addresses or operations.

Here `<W>` denotes the pin width. The actual C++ `MemoryTransactionPort` constructor takes W as a runtime argument; the simplified reference below uses a template to keep its payload widths together.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `CLK`, `RST` | Input | 1 | Clock and active-high interface reset |
| `REQ_VALID` | Input | 1 | Request available |
| `REQ_OP` | Input | 3 | Operation code |
| `REQ_ADDR` | Input | 32 | Aligned byte address |
| `REQ_WRITE_DATA` | Input | W | Positioned write/program data |
| `REQ_WRITE_MASK` | Input | W/8 | Byte enables |
| `REQ_READY` | Output | 1 | Can accept a request |
| `RSP_VALID` | Output | 1 | Response available |
| `RSP_READY` | Input | 1 | Requester accepts the response |
| `RSP_READ_DATA` | Output | W | Held read result |
| `RSP_STATUS` | Output | 3 | Held status |
| `BACK_READY`, `DONE` | Input | 1 | Backend available / operation complete |
| `RESULT` | Input | W | Backend read result |
| `STATUS` | Input | 3 | Backend status |
| `START`, `FINISH` | Output | 1 | Accept live request / release completed backend result |
| `OP` | Output | 3 | Live operation |
| `ADDR` | Output | 32 | Live byte address |
| `DATA` | Output | W | Live data |
| `MASK` | Output | W/8 | Live byte mask |

### Behavior

There is one pending bit, not a SETUP/WAIT/RESPONSE phase pipeline. START accepts a request only when the backend and response capacity are available. Completion passes directly through the response buffer. If the receiver cannot take it, the buffer captures result/status and FINISH releases the backend. Backend maintenance can then continue while that response remains held. The general FF controller uses the same response buffer directly, without this delayed-request frontend; its always-ready configuration instead returns a zero-wait response without a buffer.

#### C++ example

This reference shows the response storage and pending state. No request register is duplicated in the frontend: the native sequencer captures it on START. Control flags are binary; payloads use the project's four-state `Bits` and `Request` types. The example assumes an initial reset and compares settled behavior, not individual gate delays. It is not an additional registered behavioral implementation.

```cpp
#include "MemoryEndpointEngine.hpp" // Only value/configuration helpers.

namespace memory_example {
using namespace circuit::memory;

template<std::size_t W>
class ResponseBuffer {
    bool full_ = false;
    Bits data_ = Bits(W, L), status_ = bits(3, 0);
public:
    struct Inputs {
        bool reset = false, edge = false, valid = false, ready = false;
        Bits data = Bits(W, L), status = bits(3, 0);
    };
    struct Outputs { bool ready, valid; Bits data, status; };
    Outputs outputs(const Inputs& i) const {
        return {!i.reset && (!full_ || i.ready),
                !i.reset && (full_ || i.valid),
                full_ ? data_ : i.data, full_ ? status_ : i.status};
    }
    void step(const Inputs& i) {
        if (i.reset) { full_ = false; data_.assign(W, L); status_ = bits(3, 0); }
        else if (i.edge) {
            const bool capture = i.valid && (!full_ || i.ready) && (full_ || !i.ready);
            const bool hold = full_ && !i.ready;
            if (capture) { data_ = i.data; status_ = i.status; }
            full_ = capture || hold;
        }
    }
};

template<std::size_t W>
class Port {
    static_assert(W == 8 || W == 16 || W == 32);
    // DONE and BACK_READY rise whenever the backend is finished, at any
    // moment of the cycle. Each is captured on a clock edge before it is used.
    bool pending_ = false, done_seen_ = false, busy_seen_ = false;
    ResponseBuffer<W> response_;
public:
    struct Inputs {
        bool rising_edge = false, reset = false;
        bool request_valid = false, response_ready = false;
        bool backend_ready = false, done = false;
        Request request{bits(3, 0), bits(32, 0), Bits(W, L), Bits(W / 8, L)};
        Bits result = Bits(W, L), status = bits(3, 0);
    };
    struct Outputs {
        bool request_ready, response_valid, start, finish;
        Request request;
        Bits read_data, status;
    };
private:
    bool complete() const { return pending_ && done_seen_; }
    auto response_input(const Inputs& i) const {
        // Result and status are shown only with the captured completion.
        return typename ResponseBuffer<W>::Inputs{
            i.reset, i.rising_edge, complete(), i.response_ready,
            complete() ? i.result : Bits(W, L), complete() ? i.status : bits(3, 0)};
    }
public:
    Outputs outputs(const Inputs& i) const {
        auto r = response_.outputs(response_input(i));
        // A backend that just became busy is believed at once; one that
        // just became ready, only after an edge has seen it.
        const bool backend_ready = !busy_seen_ && i.backend_ready;
        const bool ready = !i.reset && (!pending_ || (complete() && i.response_ready))
                           && backend_ready && r.ready;
        return {ready, r.valid, ready && i.request_valid, complete() && r.ready,
                i.request, r.data, r.status};
    }
    Outputs step(const Inputs& i) {
        const auto before = outputs(i); // All FFs sample the old state together.
        response_.step(response_input(i));
        if (i.reset) pending_ = done_seen_ = busy_seen_ = false;
        else if (i.rising_edge) {
            pending_ = before.start || (pending_ && !before.finish);
            done_seen_ = i.done && !before.finish; // A finished response is not seen twice.
            busy_seen_ = !i.backend_ready;
        }
        return outputs(i);
    }
};
} // namespace memory_example
```

The backend times itself, so `DONE`, `RESULT`, `STATUS` and a rising `BACK_READY` can appear at any moment of the clock cycle. The port captures `DONE` and `BACK_READY` on a clock edge and shows the result only together with the captured `DONE`. Everything the requester sees therefore changes just after a clock edge, and a response costs one cycle more than the backend's own time. Without this, a `DONE` rising a few ticks before an edge is consumed by the port while the requester has not yet seen `RSP_VALID`, and the response is lost.

An empty response buffer bypasses its registers. On a blocked transfer it captures the payload; when consuming an old response and accepting a new one together, the old response is delivered and the new one is retained. The frontend samples START/FINISH using pre-edge values. Changing request inputs after acceptance changes its live backend pins, but does not change the sequencer's captured request. Reset clears pending/held state, not memory.

`request`, `result`, and `status` must have the pin widths listed above. The excerpt deliberately does not validate addresses or opcodes; a frontend must forward those fields to the controller, including unknown payload bits. Its internal header requires the `include` and `src/modules/memory` include paths and `SimulatorLib`. `MemoryEndpointIntegrationTest` compiles and executes the exact excerpt at W=8/16/32, including no-edge bypass, backend stalls, reset, response holding and simultaneous consume/accept.

#### Unknown inputs and timing

CLK, reset, VALID and READY must be binary and meet structural setup/hold requirements. Unknown handshake controls are protocol violations, not alternate transactions. Payload data may contain X; the controller rejects unknown opcode/address or a required mask before issuing native commands. These registers and gates have propagation delays. Examples wait for settled outputs; simulator ticks are not measured chip nanoseconds.

### Implementation

#### Structural implementation

`PENDING` is one `ClockedStateBit`. `RESPONSE` is a `MemoryResponseBuffer<W>` with an occupancy state bit, data/status registers, and bypass multiplexers; its reused register component is defined in [4.3.1](../rv32i/4.3/register.md). Live request fields cross the scope boundary through zero-delay rewires. The layout separates request forwarding, handshake control and response retention.

## 3.2.2. `MemoryResponseBuffer<W>`

One entry of response storage, shared by the zero-wait and delayed controllers. It is not a request queue or memory array.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `CLK`, `RST` | Input | 1 | Shared clock and interface reset |
| `IN_VALID`, `OUT_READY` | Input | 1 | Producer presents data / consumer accepts data |
| `IN_DATA`, `IN_STATUS` | Input | W, 3 | New response payload |
| `IN_READY`, `OUT_VALID` | Output | 1 | Input capacity / response available |
| `OUT_DATA`, `OUT_STATUS` | Output | W, 3 | Live or held response payload |
| `FULL` | Output | 1 | An older response occupies the register |

### Behavior

When empty, the input passes directly to the output. An available receiver can consume it without filling the register. Backpressure captures one response on the edge; subsequent input changes cannot alter it. When a full buffer consumes and replaces on the same edge, the old response is delivered first and the new response is retained. Reset clears occupancy and retained data/status without touching device contents.

#### C++ example

`ResponseBuffer<W>` in the preceding excerpt is the complete state/transition reference. This wrapper selects its 32-bit instance; it adds no behavior or additional state.

```cpp
namespace memory_example {
using ResponseBuffer32 = ResponseBuffer<32>;
}
```

#### Unknown inputs and timing

Controls must be known binary values. Payload FFs preserve unknown data bits. The bypass and selection gates need time to settle; “zero-wait” means no extra clock cycle, not zero propagation delay. Data/status outside OUT_VALID have no transaction meaning.

### Implementation

#### Structural implementation

`OCCUPIED` is a `ClockedStateBit`; `HELD_DATA` and `HELD_STATUS` are FF-based registers. `SELECT_DATA` and `SELECT_STATUS` choose held versus live inputs. The lower control row computes space, capture, hold and next occupancy. The buffer itself is structural; its state components can be selected independently by fidelity.

`HELD_DATA` retains W bits and `HELD_STATUS` retains 3 bits using the
[register family defined in 4.3.1](../rv32i/4.3/register.md). Including
`OCCUPIED`, the buffer retains W+4 bits: 12, 20, or 36 at W=8, 16, or 32.
An empty buffer bypasses this storage; a blocked response needs it to remain
stable. Selecting compact storage or a behavioral enclosing endpoint changes
simulation detail, not the number of logical storage bits or the response contract.

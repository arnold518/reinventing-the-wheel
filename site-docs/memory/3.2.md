# § 3.2. Memory Transactions

A shared, versioned transaction interface above the native devices in [3.1](3.1/index.md). It is a single-outstanding, aligned-word protocol, not AXI, a DDR interface, or a coherent interconnect. Width W is 8, 16, or 32; capacity is a construction parameter.

| Component | Description | Structural | Behavioral |
| --- | --- | :---: | :---: |
| `MemoryTransactionPort<W>` | Latch one request and hold its response while applying backpressure | Yes | No |

## Protocol rules

Request and response transfers occur on a known rising `CLK` edge when the corresponding VALID and READY are both 1. The sender holds VALID and its payload until transfer; it must not wait for READY before asserting VALID. At most one request is outstanding. The response is held unchanged until consumed. A new request is not accepted on the response-consume edge.

Addresses are **byte addresses** aligned to W/8. Reads return a full word. Writes/programs use positioned byte lanes; mask bit b enables byte b. ISA load sizes, sign extension, unaligned splitting, bursts, atomics, arbitration and caching are outside this port.

| `REQ_OP` | Operation | Meaning |
| ---: | --- | --- |
| 0 | READ | Read one aligned word |
| 1 | WRITE | Replace enabled bytes in writable FF/SRAM/DRAM |
| 2 | PROGRAM | NOR flash only: clear enabled bits, never restore 0→1 |
| 3 | ERASE_BLOCK | NOR flash only: restore one whole block to ones; address must be block-aligned |
| 4–7 | Reserved | Unsupported-operation response |

| `RSP_STATUS` | Meaning |
| ---: | --- |
| 0 | Success |
| 1 | Misaligned word/block address |
| 2 | Address outside configured capacity |
| 3 | Attempt to modify ROM |
| 4 | Unsupported operation |
| 5 | Native device failure |
| 6 | Unknown required request fields |
| 7 | Reserved |

Error and non-read responses have zero data. Unknown stored bits remain X even with a successful read. A zero write mask does not change contents. Read requests ignore write data/mask; erase ignores both. Validation order is unknown opcode/address → reserved opcode → required mask → word alignment → capacity → technology permission/block alignment.

`RST` resets the **transaction interface**, not memory contents. It suppresses VALID/READY and discards response delivery. An already launched native sequence drains before reuse; its writes/programs/erases are not rolled back. A request still buffered before START is discarded. Native FF storage reset is deliberately not tied to this interface reset.

## 3.2.1. `MemoryTransactionPort<W>`

Shared structural frontend. The backend receives a stable request through START and returns a stable result through DONE. It owns no memory contents and does not itself validate addresses or operations.

Here `<W>` denotes the pin width. The actual C++ `MemoryTransactionPort` constructor takes W as a runtime argument; the simplified reference below uses a template to keep its payload widths together.

### IO pins

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `CLK`, `RST` | Input | 1 | Clock and active-high interface reset |
| `REQ_VALID` | Input | 1 | Request available |
| `REQ_OP` | Input | 3 | Operation code |
| `REQ_ADDR` | Input | 32 | Aligned byte address |
| `REQ_WRITE_DATA` | Input | W | Positioned write/program data |
| `REQ_WRITE_MASK` | Input | W/8 | Byte enables |
| `REQ_READY` | Output | 1 | Can accept a request |
| `RSP_VALID` | Output | 1 | Response available |
| `RSP_READY` | Input | 1 | Requester accepts the response |
| `RSP_READ_DATA` | Output | W | Held read result |
| `RSP_STATUS` | Output | 3 | Held status |
| `BACK_READY`, `DONE` | Input | 1 | Backend available / operation complete |
| `RESULT` | Input | W | Backend read result |
| `STATUS` | Input | 3 | Backend status |
| `START` | Output | 1 | Execute the latched request; held until captured completion |
| `OP` | Output | 3 | Latched operation |
| `ADDR` | Output | 32 | Latched byte address |
| `DATA` | Output | W | Latched data |
| `MASK` | Output | W/8 | Latched byte mask |

### Behavior

IDLE accepts a request only when BACK_READY is high. SETUP gives payload registers time to settle. WAIT asserts START and waits for DONE. On the next rising edge, RESPONSE captures RESULT/STATUS. Backpressure holds that response without reissuing the operation. Backend maintenance may continue while the response registers hold their earlier result.

#### C++ example

This simplified reference includes the request registers, response registers, backend readiness, and reset—not just the phase transition. Control flags are binary; payloads use the project's four-state `Bits` and `Request` types. The example assumes an initial reset and compares settled behavior, not individual gate delays. It is not an additional registered behavioral implementation.

```cpp
#include "MemoryEndpointEngine.hpp" // Request and Bits; no device is constructed.

namespace memory_example {
using namespace circuit::memory;

template<std::size_t W>
class Port {
    static_assert(W == 8 || W == 16 || W == 32);
    enum class Phase { Idle, Setup, Wait, Response };
    static Request empty_request() {
        return {bits(3, 0), bits(32, 0), Bits(W, L), Bits(W / 8, L)};
    }
    Phase phase_ = Phase::Idle;
    Request request_ = empty_request();
    Bits result_ = Bits(W, L), status_ = bits(3, 0);
public:
    struct Inputs {
        bool rising_edge = false, reset = false;
        bool request_valid = false, response_ready = false;
        bool backend_ready = false, done = false;
        Request request = empty_request();
        Bits result = Bits(W, L), status = bits(3, 0);
    };
    struct Outputs {
        bool request_ready, response_valid, start;
        Request request; // OP / ADDR / DATA / MASK to the backend.
        Bits read_data, status;
    };

    Outputs outputs(bool reset, bool backend_ready) const {
        return {!reset && phase_ == Phase::Idle && backend_ready,
                !reset && phase_ == Phase::Response,
                !reset && phase_ == Phase::Wait, request_, result_, status_};
    }

    Outputs step(const Inputs& in) {
        if (in.reset) {
            phase_ = Phase::Idle;
            request_ = empty_request();
            result_.assign(W, L); status_ = bits(3, 0);
        } else if (in.rising_edge) {
            switch (phase_) {
            case Phase::Idle:
                if (in.request_valid && in.backend_ready) {
                    request_ = in.request;
                    phase_ = Phase::Setup;
                }
                break;
            case Phase::Setup:
                phase_ = Phase::Wait;
                break;
            case Phase::Wait:
                if (in.done) {
                    result_ = in.result; status_ = in.status;
                    phase_ = Phase::Response;
                }
                break;
            case Phase::Response:
                if (in.response_ready) phase_ = Phase::Idle;
                break;
            }
        }
        return outputs(in.reset, in.backend_ready);
    }
};
} // namespace memory_example
```

The IDLE branch captures all request fields together. Changing caller inputs afterward cannot change the backend request. WAIT captures result/status only when DONE is sampled on a rising edge. RESPONSE ignores subsequent backend result changes and holds the captured values until consumption. Reset clears these registers but cannot undo a device operation: draining launched work is the controller's responsibility.

`request`, `result`, and `status` must have the pin widths listed above. The excerpt deliberately does not validate addresses or opcodes; a frontend must forward those fields to the controller, including unknown payload bits. Its internal header requires the `include` and `src/modules/memory` include paths and `SimulatorLib`. `MemoryEndpointIntegrationTest` compiles and executes the exact excerpt at W=8/16/32, including no-edge holds, backend stalls, reset, and response backpressure.

#### Unknown inputs and timing

CLK, reset, VALID and READY must be binary and meet structural setup/hold requirements. Unknown handshake controls are protocol violations, not alternate transactions. Payload data may contain X; the controller rejects unknown opcode/address or a required mask before issuing native commands. These registers and gates have propagation delays. Examples wait for settled outputs; simulator ticks are not measured chip nanoseconds.

### Implementation

#### Structural implementation

Two phase flip-flops, logic gates, four request registers and two response registers. Each `MemoryPayloadRegister` is built from existing `FlipFlopCell` components. A one-bit field connects directly without a 1→1 splitter. Multi-byte registers display eight bit lanes per byte row. Layouts separate requests and responses, then arrange state, decoding, handshake decisions, and next-state logic in signal-flow order.

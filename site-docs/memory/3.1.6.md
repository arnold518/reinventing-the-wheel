# § 3.1.6. Scalable Memory Container

`MemoryContainer` is a scalable **native memory device**, not a controller or a sixth storage technology. It uses the same pins and behavior as the selected FF, SRAM, DRAM, ROM, or NOR-flash device in 3.1.1–3.1.5. There is no request queue, response register, or implicit transaction clock.

| Component | Description | Structural | Behavioral |
| --- | --- | :---: | :---: |
| `MemoryContainer<Model,W>` | Capacity-configurable native memory, backed by the selected technology's tested behavioral implementation | No | Yes |

The corresponding expanded implementation is the native device documented in that technology's section. The catalog factory reuses that device's behavioral implementation directly: there is no hidden circuit or second timing model. A [MemoryController](3.3.md) can drive either representation.

## Configuration

W fixes the data-pin width: 8, 16, or 32 bits. N=`depth_words` is selected at construction. Capacity is N×W/8 bytes and must fit the 32-bit byte-address range. K=`words_per_row` describes physical row organization, not host paging. FF does not use K; the other container models accept K=1/2/4/8/16 dividing N.

| Parameter | Default | Meaning |
| --- | ---: | --- |
| `depth_words` | 4 in C++; 4096 in the Python factory | Number of addressed words |
| `paged` | 1 | Allocate host pages only when contents differ from the initial fill |
| `max_resident_bytes` | 67,108,864 | Content allocation budget; DRAM also checks row metadata |
| `record_history` | 1 | Record memory-content history |
| `max_history_bytes` | 16,777,216 | Fail-fast history budget; no silent eviction |

Geometry and native timing parameters follow the selected device. `guard_ticks`, `refresh_interval_ticks`, and `expanded_storage` belong to controller/assembly configuration; they do not add behavior to a standalone container. In particular, a DRAM container **does not refresh itself**.

Host pages cover 4096 simulated bytes and store value/known masks. Untouched capacity does not allocate content pages. DRAM keeps metadata only for visited rows, and ROM parses only the supplied image prefix. Budgets are not a process-RSS cap: event history, objects, temporary buffers, and allocator overhead also consume memory. Disable memory and simulator histories separately for long performance runs.

Python creates a 1 MiB direct FF device as follows:

```python
memory = circuit_backend.create_memory_container(
    "MEMORY", "ff", data_width=32, depth_words=262144,
    parameters={"paged": "1", "record_history": "0"},
)
```

The C++ factory is `createMemoryContainer<32, circuit::memory::FFModel>("MEMORY", config)`; it constructs the native implementation through `Component::createWithContext`. Runtime-width code uses `createMemoryContainer(name, width, technology, config)`. Catalog IDs are `memory.device.<technology>.<width>`. The `memory.scalable.*` IDs name **transaction endpoints** built around this device (the form every RV32I core uses), not the device contract itself. Those endpoints default to their fused behavioral form; expanding one in the explorer shows its controller around this compact native device, without expanding the storage into cells.

## 3.1.6.1. `MemoryContainer<Model,W>`

The selected technology fixes the native pin schema. Changing capacity does not change the pins; changing technology may.

### IO pins

The following table is the FF-model interface used by the embedded example and strict single-cycle core.

| Pin | Direction | Width | Description |
| --- | --- | ---: | --- |
| `WORD_ADDR` | Input | 32 | Word index, not byte address |
| `WRITE_DATA` | Input | W | Positioned store bits |
| `WRITE_MASK` | Input | W/8 | Enabled byte lanes |
| `WE`, `READ_EN` | Input | 1 | Rising-edge write enable; asynchronous read enable |
| `CLK`, `RST` | Input | 1 | Write clock; active-high storage reset |
| `READ_DATA` | Output | W | Selected word, or zero when disabled/out of range |
| `FAULT` | Output | 1 | Invalid active access; X for unknown required controls |

Other models expose the complete interfaces in [SRAM](3.1.2.md), [DRAM](3.1.3.md), [ROM](3.1.4.md), and [NOR flash](3.1.5.md), including DRAM `ROW_OPEN` and flash `WRITE_ENABLED`. They do not expose REQ/RSP pins. A universal requester connects to a matching technology controller, not directly to these native pins.

### Behavior

| Model | Access and storage rules | Direct single-cycle CPU suitability |
| --- | --- | --- |
| FF | Asynchronous read; masked write on LOW→HIGH CLK; native reset clears all words | Yes, with sufficient combinational settling time |
| SRAM | Asynchronous CE/WE/OE; address/data changes restart timed access phases | Reads can settle within a long cycle; writes need deliberate clock-boundary integration |
| DRAM | ACT, column READ/WRITE, PRECHARGE, REFRESH; destructive sampling, restore, retention | Requires command sequencing; not an instantaneous RAM |
| ROM | Asynchronous read; construction image with zero-filled tail; no runtime write | Read-only access can settle within a cycle |
| NOR flash | WREN, timed PROGRAM/ERASE, READ; programming clears bits and erase restores ones | Requires command sequencing for modifications |

The strict single-cycle system currently uses the FF model for both instruction and data storage. It ties native memory RST low so resetting the CPU preserves its images. PC, registers, and data-memory writes use the same edge. Capacity affects host storage, not a mandatory number of CPU cycles.

Image provisioning through `initializeMemoryBytes` is allowed only before the first evaluation. It is distinct from runtime pins and from reset; reset never reopens provisioning. ROM/flash provisioning describes an initial image, not an instruction that changes read-only/flash programming rules. Native-device references remain authoritative for all technology-specific behavior.

#### C++ example

This four-state FF reference spells out the direct-access behavior. It reuses only value helpers and bounded `MemoryStorage`, not the simulator's device algorithm. Native SRAM/DRAM/ROM/flash use the complete behavioral examples in their respective sections; wrapping them as containers adds no protocol state.

```cpp
#include "modules/memory/DigitalMemory.hpp"
namespace memory_native_example {
using namespace circuit::memory_device;
template<size_t W> class FF {
    MemoryStorage storage;
    LogicValue previous = X;
public:
    struct Inputs {
        Bits WORD_ADDR = bits(32,0), WRITE_DATA = Bits(W,L),
             WRITE_MASK = Bits(W/8,L);
        LogicValue CLK=L, RST=L, WE=L, READ_EN=L;
    };
    struct Outputs { Bits READ_DATA; LogicValue FAULT; };
    explicit FF(size_t words)
        : storage(words,W,X,true,{true,64*1024*1024,16*1024*1024}) {}
    Outputs evaluate(size_t time,const Inputs& i) {
        const bool address_known=known(i.WORD_ADDR);
        const bool mask_known=known(i.WRITE_MASK);
        const auto word=number(i.WORD_ADDR);
        const bool selected=address_known && word<storage.capacityWords();
        LogicValue fault=L;
        if(i.WE!=L || i.READ_EN!=L) {
            if(!binary(i.WE)||!binary(i.READ_EN)||!address_known||(i.WE==H&&!mask_known)) fault=X;
            else if(!selected) fault=H;
        }
        if(i.RST==H) storage.fill(time,L);
        else if(!binary(i.RST)) storage.fill(time,X);
        else if(previous==L && i.CLK==H && i.WE==H && selected && mask_known && fault==L) {
            for(size_t byte=0;byte<W/8;++byte) if(i.WRITE_MASK[byte]==H)
                storage.writeLogic(time,word*(W/8)+byte,
                    Bits(i.WRITE_DATA.begin()+byte*8,i.WRITE_DATA.begin()+(byte+1)*8),true);
        }
        previous=i.CLK;
        Bits result(W,L);
        if(!binary(i.READ_EN)||(i.READ_EN==H&&!address_known)) result.assign(W,X);
        else if(i.READ_EN==H&&selected) result=storage.readLogic(word*(W/8),W/8);
        return {result,fault};
    }
};
}
```

#### Unknown inputs and timing

Stored Z becomes X. The FF model reads without any clock edge and writes only on a known LOW→HIGH transition. Unknown reset makes FF contents unknown; unknown required access controls produce FAULT=X. Its output propagation takes simulator ticks, so “single-cycle” does not mean zero delay. Native SRAM phases and DRAM/flash deadlines remain active; they are not converted into CPU-clock waits or removed by selecting a large capacity.

### Implementation

The factory selects the existing native behavioral device and labels the leaf `MemoryContainer<model,width>`. FF reuses the FF-array behavior; SRAM reuses the complete access-sequence model; DRAM/ROM/NOR reuse their native command/read models. All share host allocation/provisioning support, not one universal cell algorithm.

For a visible transaction wrapper, construct `MemoryEndpoint` with `expanded_storage=0`: its structural controller drives a scalable device. The endpoint's fused behavioral alternative is `BehavioralMemoryEndpoint`, documented in 3.3. Do not put the legacy `container` relay in front of a native container; use the actual technology controller.

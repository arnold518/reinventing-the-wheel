# § 5.3. Memory Subsystem

Main memory, as the bus sees it: one memory with two ports, `I_` for
instruction fetch and `D_` for data. Inside, an optional small cache sits on
each port, the [two-port arbiter](../memory/controllers.md#353-twoportmemoryarbiterw)
takes turns, an optional shared cache sits below it, then one memory
endpoint. The shared-memory arrangements of
[§ 4.7](../rv32i/memory-systems.md) and the memory-system experiments of
[§ 4.8](../rv32i/experiments.md#memory-systems) are built from this part.

| Component | Description | Structural | Behavioral |
| --- | --- | :---: | :---: |
| `MemorySubsystem` | Two ports, optional caches, an arbiter and one memory | Yes | No (its endpoint, caches and arbiter have compact forms) |

Catalog: `memory.subsystem.32`.

| Parameter | Values | Default |
| --- | --- | --- |
| `technology` | `ff`, `sram`, `dram` | `ff` |
| `words` | A power of two in 16–2^28 (an accepted construction parameter, not a tested capacity range) | 65536 (256 KiB) |
| `caches` | `none`, or `default`: a read-only instruction cache and a write-through data cache, each four sets of 16-byte lines | `none` |

These are the catalog parameters a system description uses. Built from C++
(`MemorySubsystemConfig`), the part takes the full form: any memory
endpoint configuration, any cache configuration per port and for the shared
cache, the arbiter's burst length, and optional invalidation inputs
`INV_L1` (both port caches) and `INV_L2` (the shared cache). § 4.7 and § 4.8
use that form.

## IO pins

| Pin | Direction | Width | Meaning |
| --- | --- | ---: | --- |
| `CLK`, `RST` | Input | 1 each | Clock; reset of the ports, caches and arbiter (not of the stored data) |
| `<P>REQ_VALID`, `<P>REQ_OP`, `<P>REQ_ADDR`, `<P>REQ_WRITE_DATA`, `<P>REQ_WRITE_MASK`, `<P>RSP_READY` | Input | 1, 3, 32, 32, 4, 1 | Requests, for P = `I_`, `D_` |
| `<P>REQ_READY`, `<P>RSP_VALID`, `<P>RSP_READ_DATA`, `<P>RSP_STATUS` | Output | 1, 1, 32, 3 | Answers on the corresponding port |
| `I_CLK`, `I_RST`, `D_CLK`, `D_RST` | Input | 1 each | Port clocks, unused (everything runs on `CLK`) |
| `INV_L1`, `INV_L2` | Input | 1 each | Only with invalidation inputs: invalidate the port caches / the shared cache |

## Behavior

Both ports see the same memory: a word written through `D_` is fetched
through `I_` (once any cached copy is replaced). Each port answers with the
memory's statuses: Range past the last word, Alignment for a misaligned
word. Reset clears the ports and caches but keeps the memory image, so a
loaded program survives it.

The two ports contend at the arbiter after any cache lookup. A request or
response waits through the same valid/ready rules as the other memory
components. When both ask in the same cycle, the fetch port wins after
reset and the arbiter then alternates (round robin); the losing port must
keep its request up until its `REQ_READY` rises. Without caches, `D_REQ_READY` rises only
while the data port is asking, so an idle data port reads not-ready, which
the valid/ready handshake allows. The endpoint's technology determines alignment, masks, range
errors and physical access/refresh waits; these are not replaced with a
fixed subsystem latency.

With caches, there is no instruction/data coherence mechanism: invalidation
is tied off. A data write does not invalidate an instruction-cache copy, so
self-modifying code must not assume a subsequent fetch sees the new word.
Program loading takes place before reset and execution. Devices stay on
separate bus targets and never pass through these caches.

| `caches` | A fetch hit | A fetch miss | A store |
| --- | --- | --- | --- |
| `none` | — | waits for the arbiter and the memory | waits for the arbiter and the memory |
| `default` | answered in the lookup cycle | fills a 16-byte line | written through to memory |

## Implementation

| Part | Contents |
| --- | --- |
| `INSTRUCTION_CACHE`, `DATA_CACHE` | `Cache<32>` on each configured port (with `caches = default`, scalable storage); invalidation tied off unless the invalidation inputs exist |
| `ARBITER` | `TwoPortMemoryArbiter<32>`: `I_` side from the fetch path, `D_` side from the data path |
| `SHARED_CACHE` | An optional read-write `Cache<32>` between the arbiter and the memory (C++ form only) |
| `RAM` | The memory endpoint of the chosen technology ([§ 3.5](../memory/controllers.md)); a large memory selects the native device's scalable form |

The program loader writes straight into `RAM`'s storage before the run.

There is no whole-subsystem compact leaf. Its endpoint, arbiter and caches
retain their own structural or compact implementations. The current recipe
instantiates the caches and the arbiter by class; these are not cache
families selected from the system description, and a description can only
choose no caches or the default pair. Separate instruction and data memories
(§ 4.7's arrangement A) are not this part: they are two endpoints.

**Timing.** Propagation and access timing come from the chosen child parts,
and the whole connected machine needs its own clock certificate. There is
no stored subsystem delay table or single-cycle promise for a cache miss.
The published machine certificates cover specific FF configurations; they
are not a sweep over every accepted depth, technology and cache option.
Structural unknown fields follow the endpoint and arbiter rules; numerical
program checks use known binary traffic after reset.

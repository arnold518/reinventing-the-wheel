# § 5.7. Experiments

Three questions about the machines of this chapter, answered by running the
same games on each:

1. Is the bus-built machine the same machine as the fixed device system it
   replaced?
2. What does a second bus cost, behind a pass-through bridge and behind a
   registered one?
3. How fast may the machines be clocked, in realistic gate timing?

## Method

Each run is one guest fixture (the program and its scripted button events)
on one machine, checked as in [§ 5.6](5.6.md#how-a-run-is-checked); a run
that fails any check is not reported. The machine comparison runs the
bring-up program and the five short game versions; cycle comparisons use the
`unit` timing profile at a 1000-tick clock, and all parts are in their
compact forms, which run on delays proven on their gates.
`tools/system/run-experiments.py` runs the campaign one job at a time; its
summaries are in `site-docs/assets/system/results/` and the tables below are
generated from them (`tools/system/results-tables.py`).

| Machine | Description |
| --- | --- |
| One bus | `games-machine`: core, memory and devices on one bus |
| Two buses | `games-machine-two-bus`: memory and video on a system bus; the devices behind a pass-through bridge on a peripheral bus |
| Registered bridge | `games-machine-registered-bridge`: the same with a bridge that registers each request and answer |

## The new machine equals the old one

The fixed `RV32IMDeviceSystem` was measured before it was retired, with the
game fixtures of that time (retired in turn on 2026-11-03; this table keeps
their measured results). The one-bus machine gave the same cycle counts and
the same frames, console text, reports and device reads:

<!-- results: baseline -->
| Game | Memory | Old machine cycles | New machine cycles | Same results | Events (old → new) |
| --- | --- | ---: | ---: | :---: | --- |
| Bring-up | ff | 38,811 | 38,811 | yes | 15,181,178 → 11,000,184 |
| Pong | ff | 88,367 | 88,367 | yes | 33,391,339 → 24,655,432 |
| Snake | cached-ff | 260,970 | 260,970 | yes | 443,666,985 → 207,853,755 |
<!-- /results -->

The machines differ in structure, not in time: the bus is the old router
and arbiter, rearranged by the description, and the devices' new register
front ends answer in the same cycles. The new machine needs fewer simulation
events; one likely reason (not measured separately) is that the front end
decodes an offset with one `Decoder<n>` instead of a 32-bit comparison per
register.

## One bus or two

<!-- results: machines -->
| Game | One bus | Two buses | Registered bridge | Two buses vs one | Registered vs one |
| --- | ---: | ---: | ---: | ---: | ---: |
| Bring-up | 3,714 | 3,754 | 3,834 | +40 (+1.08%) | +120 (+3.23%) |
| 2048 | 32,012 | 32,044 | 32,108 | +32 (+0.10%) | +96 (+0.30%) |
| Sokoban | 43,273 | 43,311 | 43,387 | +38 (+0.09%) | +114 (+0.26%) |
| Snake | 28,194 | 28,233 | 28,311 | +39 (+0.14%) | +117 (+0.41%) |
| Pong | 13,324 | 13,361 | 13,435 | +37 (+0.28%) | +111 (+0.83%) |
| Tetris | 50,860 | 50,896 | 50,968 | +36 (+0.07%) | +108 (+0.21%) |
<!-- /results -->

All three machines produce the same frames and console text for every
program; their reports differ only in the timer samples, which count clock ticks
(the table generator checks this and refuses to print otherwise).

The extra cycles are exactly the number of device accesses. Pong's short
version, for example, makes 22 device reads, writes 10 console bytes,
presents 3 frames and pops 2 button events: 37 accesses, 37 extra cycles
with two buses, 111 (3 × 37) with the registered bridge. Instructions and memory stay on the system bus
and do not pay at all.

| One device access | One bus | Two buses | Registered bridge |
| --- | :---: | :---: | :---: |
| Routers crossed | 1 | 2 | 2 |
| Bridge register stages | — | 0 | 2 (request, answer) |
| Extra cycles vs one bus | 0 | 1 (second router) | 3 (second router + 2 stages) |

Why a pass-through bridge still costs a cycle: every bus's router holds a
request for one clock edge before offering it ([§ 5.2.1](5.2/router.md)). A
device access now crosses two routers, so it pays that edge twice; the
bridge itself adds nothing. The registered bridge adds an edge in each
direction on top.

Why build two buses then? In a real machine the slow devices, with their
long wires and narrow ports, would otherwise lengthen the clock period of
the fast path to memory. Here the devices are flip-flop logic on the same
clock as everything else, so the second bus shows only its cost; the
[clock](#clock) shows that it does not lengthen the critical path either.

## Clock

The safe-clock analyzer certifies each machine: the shortest period at
which every register meets its setup time, with the machine's inputs
changing one tick after a falling edge.

<!-- results: clocks -->
| Machine | Memory | Unit profile (ticks) | Embedded profile | Embedded clock | Limiting path (embedded) |
| --- | --- | ---: | ---: | ---: | --- |
| `games-machine` | ff | 92 | 4,464 ps | 224 MHz | CORE.IMEM_RSP_READ_DATA |
| `games-machine` | cached-ff | 84 | 4,254 ps | 235 MHz | MEMORY.INSTRUCTION_CACHE.CONTROLLER pending bit |
| `games-machine-two-bus` | ff | 90 | 4,464 ps | 224 MHz | CORE.IMEM_RSP_READ_DATA |
| `games-machine-registered-bridge` | ff | 90 | 4,464 ps | 224 MHz | CORE.IMEM_RSP_READ_DATA |
| `games-machine-leds` | ff | 94 | 4,470 ps | 224 MHz | MEMORY.ARBITER.I_RESPONSE.HELD_DATA write enable |
<!-- /results -->

The limiting path of the one-bus machine is the fetch answer arriving at
the core (embedded) or the memory arbiter's held answer (unit). Adding a
bridge, registered or not, does not lengthen it. The games of
[§ 5.6](5.6.md) run at 4.5 ns, within the listed FF-memory
configurations' certificates; the listed cached-FF configuration certifies
at 4.254 ns (4,254 ps), so rounding that down to 4.25 ns would be too short.

The table's numbers are simulated timing contracts under the stated binary
input boundary, including setup and hold constraints. They are not measured
clock rates of fabricated hardware, nor a certificate for every memory size,
prediction setting or checked-link configuration.

## Reproducing a selected run

The existing runner accepts one fixture and machine at a time. For example,
with the built native tool:

```sh
CIRCUITSIM_TIMING_PROFILE=embedded build-milestone/system_experiment \
  --guest bringup --machine games-machine-two-bus \
  --memory ff --fidelity compact --period 4500
```

This runs a new simulation and prints a checked result JSON. The campaign
script `tools/system/run-experiments.py` runs selected games/machines
serially; `tools/system/results-tables.py` validates the saved summaries and
regenerates the published result rows. Reformatting a table is not a new run.

## Limits

- The devices are as fast as the memory and no bus has more than two
  masters on one target, so slow devices and heavy arbitration are not
  measured.
- Cycle counts depend on the fixtures' short scripts (three actions per
  game); they compare machines, they do not rate the games.
- Host times are for one development machine, with other work running.
- The recording browser check covers playback of a captured run, not
  WebAssembly execution of that game; games run natively only.
- There is no independent randomized legal-traffic bus reference campaign,
  technology × cache sweep, or automatic protocol proof from the port
  checker's three flags. These limits are additional to the selected guest
  models and clock certificates reported above.

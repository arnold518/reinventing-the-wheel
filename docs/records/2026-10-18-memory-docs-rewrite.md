# Memory chapter rewrite and the timing-aware page template

Started: 2026-10-18. Status: open. Code state: branch `realistic-timing` at
`5d7ddc5` (phase 8 of the [realistic-timing plan](2026-10-16-realistic-timing-plan.md)).

## Summary

The owner asked for a complete rewrite of the public memory chapter
(`site-docs/memory/`, caches excluded for now), using the current pages only
as a guide, and for a page template that reflects the timing work: profiles,
proven delays, behavioral delays. This record holds the survey of the current
pages, the comparison with the code, and the template design. No public page
has been changed yet.

## 2026-10-18 — Survey of the current pages

**Scope read:** all of `site-docs/memory/` except 3.4 (about 5,000 lines),
the ALU8 chapter (2.1–2.6), RV32I building blocks and cores (4.3–4.5), the
clock-analysis contract (4.2 `timing.md`), `execution.md`, the timing tests
page and the experiments page.

**The repeated component template** (every component page in chapters 2–4):

1. Page header: one paragraph, then a component table with `Structural` and
   `Behavioral` Yes/No columns, then a "Conventions" block.
2. Per component: `IO pins` (table) → `Behavior` (prose or truth table) →
   `C++ example` (simplified binary reference, "not the simulator") →
   `Unknown inputs and timing` → `Implementation` (`Structural
   implementation`, `Behavioral implementation`) → `Examples` (generated
   checkpoint table from a `<!-- simulator-examples: SCENARIO TEST -->`
   marker, an embedded simulator iframe, an "Open in the simulator" button)
   → `Source and tests` (links and a test/coverage table).

**How the pages describe time today.** Five recurring forms:

| Form | Example text | Where |
| --- | --- | --- |
| Fixed small tick counts | "Both gates have a one-tick delay"; "totaling three abstract delay ticks" | ALU8 2.1, memory helpers ("publishes after one tick") |
| Disclaimers | "abstract simulator ticks, not calibrated hardware timing"; "Simulator ticks are abstract time units" | Almost every page, often twice |
| No latency | "There is no single declared structural `Adder8` latency; consumers must allow the circuit to settle" | ALU8 2.1–2.6, RV32I 4.3 |
| Behavioral delay, qualitative | "receives an output delay table characterized from its structural counterpart … a supported delay twin … can publish when that case settles, within the table's bound" | ALU8 conventions and each behavioral subsection; memory 3.1; RV32I 4.3 |
| Memory phases in parameters | `phase_ticks` P with a 4P SRAM table, DRAM P/2P/3P command table, `guard_ticks`, `program_ticks` | Memory 3.1.2–3.1.5, 3.3 |

The clock is described separately (4.2 `timing.md`, experiments page) with
certificates of 166 / 80 / 100 / 102 ticks dated 2026-10-13. Checkpoint
tables come from tests run in the `unit` profile and show absolute tick times
without naming the profile.

## 2026-10-18 — Comparison with the code

| Topic | What the pages say | What the code does now |
| --- | --- | --- |
| Unit of time | Abstract ticks only | `TimingProfile`: `unit` (1 tick per gate), `embedded` (65 nm, FO4 30 ps) and `desktop` (32 nm); in the realistic profiles 1 tick = 1 ps. Gate delays from logical effort (NOT 1 FO4, NAND 1.35, NOR 1.55, AND/OR via NAND/NOR + inverter, XOR 4 FO4); wiring parts 0. The profile is recorded in each build manifest (`timing=embedded`) |
| Gate delay rule | Transport delay implied | Inertial: a gate replaces a pending, unpublished change (phase 2); the delay twin follows the same rule |
| Behavioral delay | "characterized from its structural counterpart", no numbers | `PartDelays` per profile: arcs input→output with a minimum and a maximum (e.g. 8-bit adder A→Cout 3–18 ticks in `unit`, 102–936 ps in `embedded`), arcs per control value, clock-to-output `launches`, per-input `setup`, `internal_period`, `fixed_inputs`, `self_timed` / `clocked_interface`, evidence ("proven on … structural"). Generated by `part_delay_tables`, kept at a fixed point, verified per profile |
| How good the behavioral delay is | Not stated | `DelayRuleTest`: the compact part is never earlier than the gates; its tightness is measured (typical ≥ 70 %, worst ≥ 90 % of the table delay, or a recorded exception); `--strict-settling` variant |
| Delay twin | "publish sooner … within the table's bound" | `DelayTwin` / `GateTwin`: times the current input values through the part's gate list; never later than the table |
| Setup checks in simulation | "not a setup/hold model" (register, register file, flip-flop pages) | A compact part with a table watches its own setup times and counts violations; experiment runs require zero; flip-flop and SRAM-cell contracts are measured per profile (`embedded` flip-flop setup 231 ps, clock-to-Q 132–175 ps) |
| Large geometries | 4,096-cell limit; behavioral device for size | Supported large memories use a delay estimate grown from proven smaller geometries; arrays get wordline/bitline/sense delays growing with rows; 32-row SRAM subarrays joined by `MemoryWire` / `MemoryBus` |
| Memory control | "terminal timed digital primitive" (SRAM access control, DRAM/NOR command control, ROM address control, controller `DEVICE_CONTROL`) | Built from gates: `MemoryRequestCheck`, `StaticMemorySequencer`, `CommandMemorySequencer`, `MemoryTimer`, `MemoryDelayLine`, `Synchronizer`, `SymbolicDiffer`, `KnownBits`, `PowerOnReset`, `ProtocolStableData` |
| Memory timing values | `phase_ticks` 32, P-multiples | Datasheet intervals in the realistic profiles (SDRAM MT48LC16M16A2 tRCD = CL = tRP = 18 ns, tREFI 7.8 µs, 64 ms retention; NOR S29GL256S tACC 120 ns, program 150 µs, sector erase 410 ms); clocked on-chip SRAM macro; DRAM commands counted in cycles (ceil(interval / period)); static access cycles from proven tables (`staticAccessCycles`) |
| Protocol | Op 4 reserved, no bursts | Burst read (op 4), `block_words`, LAST and SPACE |
| Clock | Certificates 166 / 80 / 100 / 102 ticks | Per profile: single 7,164 / 4,986 ps, baseline 3,354 / 2,334 ps, advanced 4,104 / 2,858 ps (`embedded` / `desktop`); `unit` 166 / 80 / 94 (FF), 158 (clocked SRAM), 92; cached and shared-memory roots certified too |
| Checkpoint tables | Absolute ticks, profile unnamed | Tests run in `unit`; realistic profiles are covered by profile-selecting tests (`RV32IProfileSweepTest` and others) |

Conclusion: the template has no place where a proven number can go. Timing is
either a hand-typed tick count (true only in `unit`), a disclaimer that is no
longer true, or a qualitative paragraph repeated on every page.

## 2026-10-18 — Template design (proposal)

**Principle:** pages state the mechanism once, in one shared page, and show
numbers only from generated tables, like the example rows already are. No
hand-typed delay numbers on component pages.

1. **New shared page: "Time and delay".** One place (for example a section of
   the site introduction, linked from every chapter) explaining: profiles and
   what a tick is in each; gate delays (logical effort, inertial rule);
   structural timing (the gates themselves); behavioral timing (proven table
   with minimum and maximum, delay twin, the never-earlier rule and its
   measured tightness); clocked parts (clock-to-output, setup, hold, measured
   flip-flop contract, setup checks in simulation); large-geometry estimates;
   the safe-clock analysis. Every per-page disclaimer is replaced by a link.
2. **Split the per-component section** `Unknown inputs and timing` into
   `Unknown inputs` (four-state rules, unchanged in spirit) and a new
   **`Timing`** section placed after `Implementation`:
   - *Generated delay table*: marker `<!-- timing-table: CONTRACT -->`.
     Columns: path (input → output, or clock → output, or setup on input),
     then `unit` (ticks), `embedded` (ps), `desktop` (ps), each as
     minimum–maximum. Arcs per control value appear as grouped rows (for
     example per ALU operation). Rows come from the proven tables, so they
     cannot drift from the code.
   - *Structural timing*: the longest gate path in words (what limits it),
     no numbers typed by hand.
   - *Behavioral timing*: a short standard line generated with the table:
     evidence ("proven on …"), whether a delay twin is used, and the
     delay-rule tightness (typical / worst share) with any recorded exception.
   - *Clocked parts*: clock-to-output, setup and internal period in the same
     table; a note that simulation counts setup violations.
3. **Memory pages add `Access timing`** for devices, controllers and
   endpoints: how the access time is built (decode, wordline, bitline with
   rows, sense, wire across subarrays; or datasheet intervals for external
   parts), then a generated latency table per profile, in ps and in cycles at
   the certified clock (read, write, DRAM row hit / closed / conflict,
   refresh, NOR read / program / erase). These replace the `phase_ticks`
   tables.
4. **Example tables name their profile.** The marker gains an optional
   profile (`<!-- simulator-examples: SCENARIO TEST profile=unit -->`,
   default `unit`); the table caption states it. Where timing is the point
   (memory access), a second table in `embedded` can be generated. The
   embedded simulator takes the same choice once the visualizer's profile
   selection (phase 8) exists.
5. **Header table** gains a column "Timing" (for example "gates",
   "proven table", "table + twin", "self-timed, clocked interface").
6. **C++ references** stay short, describe values only, and say once that
   timing is in the Timing section. The long sequencer listings of 3.3 are
   dropped; the generated latency tables carry the timing.

**Generation and checks.** A small generator (from `part_delay_tables` data
per profile, plus the latency probes already used in the records) fills the
`timing-table` and latency markers during `tools/build-pages.sh`; a
documentation test checks that every marker names a known contract and that
the committed rows match. The page tests that compile the long C++ listings
(`MemoryDeviceDocumentationTest`, `MemoryEndpointIntegrationTest`) are
rewritten for the shorter references; `RegisterFileDocumentationTest`'s
assertion that `memory/3.4.md` does not exist is resolved with the chapter
renumbering.

**Rollout:** the memory chapter is written in the new template first; the
shared "Time and delay" page with it. ALU8 and RV32I pages keep their content
and get the same `Timing` section afterwards (a mechanical change once the
generator exists). Open until the owner confirms the template.

## 2026-10-18 — Delay-table generator (implemented)

- `tools/mkdocs_timing.py`, a MkDocs hook registered in `mkdocs.yml`:
  `<!-- timing-table: KEY -->` becomes one table of the stored proven delays
  of KEY (a name from `part_delay_tables`, for example
  `arithmetic.adder.width8.behavioral.direct` or
  `memory.sram.device.32.behavioral@depth=64`). Rows: every input → output
  path (merged over control values, with a note), clock → output launches,
  setup per input, the internal clock period. Columns: `unit` (ticks),
  `embedded` (ps), `desktop` (ps), minimum–maximum. A generated line names
  the evidence, held inputs (such as `RST` = 0), self-timing, and whether a
  delay twin is attached (from `NoGateList.generated.inc`).
- The hook parses the three generated table files directly; no build or
  WebAssembly export is needed, and the numbers are the ones the simulator
  uses.
- `TimingTableDocumentationTest` (CTest, labels documentation, timing,
  unit): all 754 stored tables render with the same paths in every profile;
  known values (8-bit adder A → Cout: 3–18 ticks, 102–936 ps, 71–652 ps);
  clocked parts show launches, setup and internal period; every marker in
  `site-docs/` names a stored table; an unknown name is refused. Passed
  (run directly; the CTest registration takes effect at the next configure).
- Not yet: no page uses the marker; the latency tables for memory access and
  the delay-rule tightness line need their own data (latency probes, a
  `DelayRuleTest --report` export).

**Corrected against the code** (each checked in the source or with
`VisualizerSessionProbe`):
- SRAM: access control is a `MemoryTimer` of gates and delay lines with a
  `READY` output (stage order settle → precharge → decoder replica → row →
  bitline → sense → READY; writes drive from the end of precharge);
  the device has `READY`; the clocked macro (`clocked=1`, `CLK`); 32-row
  subarrays with global wires and a return bus. The `P/2P/3P/4P` phase
  table is gone.
- DRAM: command control as gates (flip-flops, delay-line chains, a
  one-stage sampler, power-on reset); a command can be taken in the
  completing cycle; READ_BURST is code 6; the ACTIVATE steps sum to tRCD,
  READ is CL, the PRECHARGE steps sum to tRP (checked: 18 ns / 13.75 ns).
- ROM: `ROMAddressControl` holds the address in a `MemoryTimer`, outputs
  row/slot bit fields (not X for out-of-range addresses), `OUTPUT_ENABLE`
  without an address check, and `READY`; the device has `READY`.
- NOR flash: command control as gates; the program/erase pulse lengths are
  `program_ticks`/`erase_ticks` from the profile (S29GL256S in the
  realistic profiles); BUSY falls one edge after the chain's end is sampled.
- Transactions: READ_BURST (op 4) for SRAM/ROM/DRAM; REQ_READY from
  registered state only; the port's `LAST` and `SPACE` pins; the
  validation order including bursts.
- Controllers: the configuration table (`access_cycles`,
  `refresh_interval_cycles`, `clocked`, `block_words` for bursts;
  `phase_ticks`, `guard_ticks`, `refresh_interval_ticks` only
  range-checked); the gate-level sequencers instead of a "terminal timed
  sequencer"; `MEM_READY` and `MEM_ROW_OPEN`.
- A first draft said the NOR controller synchronizes `BUSY` in two stages;
  the code has no controller-side synchronizer (the devices sample their
  own chains in one stage). Corrected on three pages before commit.
